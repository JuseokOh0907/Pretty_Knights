# 006. 구역 전환과 포탈

- **상태:** 확정
- **결정일:** 2026-08-05
- **대체:** 결정 005 §2 "갭 + 페이드 전환" 은 방 단위 구조가 폐기되면서 함께 폐기됐다. 이 문서가 그 자리를 대신한다.

---

## 1. 포탈은 밟는 것으로 발동하지 않는다

`BoxCollider2D` 의 `Is Trigger` 안에 들어와 있는 **상태 + 사용 키**를 눌러야 이동한다.

```
트리거 안에 들어감  →  사용 버튼이 화면에 뜬다
사용 키 / 버튼      →  전환
```

### 이 선택이 없앤 문제

밟는 즉시 발동하는 방식에는 **도착 지점이 반대편 포탈 트리거 안이면 무한 왕복**하는 함정이 있다.
배치 규칙("도착 지점을 포탈에서 2칸 이상 떨어뜨린다")으로 막으면 언젠가 반드시 뚫린다.
사용 키 방식은 이 문제 자체를 없앤다 — 도착해도 버튼을 안 누르면 아무 일도 없다.

**부수적으로 트리거 크기 제약도 사라졌다.** 오발동이 없으므로 스프라이트와 같은 2 × 2칸으로 잡는다.

## 2. 포탈은 단방향이다

되돌아가는 짝 포탈을 두지 않는다. 던전에서 나오는 길은 **탈출 스킬** 하나뿐이다.

- 목적지는 `AreaDefinition.EscapeTo` 가 구역마다 들고 있다 (보통 그 던전의 입구)
- 실행은 `AreaTransition.RequestEscape()`
- 스킬 시스템이 없으므로 지금은 배선만 되어 있고 호출부가 비어 있다

## 3. areaId 는 이름이 아니라 번호다

```
areaId = 테마번호 × 100 + 층

    0        미지정 (구역 기록이 없는 옛 세이브)
    1 ~  99  거점        1 시작 신전 · 2 숲 · 3 던전 입구
  101 ~ 189  테마 1 Goblin   층 (101 = 1F · 102 = 2F · 103 = 3F)
       190   테마 1 Goblin   보스 보상방
  201 ~ 290  테마 2 Orc
  301 ~ 390  테마 3 Vampire
```

**보상방은 90번을 쓴다** (2026-08-05 추가). 3F 보스를 처치하면 그 자리에
금색 보상 포탈이 열리고 이 구역으로 간다. 층 번호 대역(1~89)을 침범하지 않아
환생으로 층이 늘어나도 충돌하지 않는다.

**히든 방은 구역이 아니다.** 오브젝트로 입구를 막아 만드는 공간이므로
같은 층 안에 있고 별도 areaId 를 갖지 않는다.

### 왜 문자열이 아닌가

`goblin_2f` 같은 이름 ID 는 **테마 이름이 그 층의 내용이라는 전제**를 깔고 있는데 그게 성립하지 않는다.
Goblin 2F 에는 고블린이 두 종류 배치될 예정이고, 배치가 바뀌면 ID 가 곧 거짓말이 된다.
번호는 그 전제를 아예 갖지 않는다.

번호 규칙 덕분에 **환생마다 층이 추가되어도**(005 §6-3) 104, 105 로 이어지고
테마가 늘어도 401 로 이어진다. 층 수를 코드 상수로 박지 않는다는 제약을 그대로 만족한다.

**세이브에 그대로 기록되므로 한 번 정한 번호는 바꾸지 않는다.**

## 4. ScriptableObject 는 씬 오브젝트를 참조할 수 없다

이 한 줄이 구조 전체를 결정했다. "포탈 도착 지점을 링크한 에셋" 하나로는 만들 수 없다.

```
AreaDefinition.asset   번호만 선언 (씬 비종속)
        ↕  번호로만 이어진다
AreaAnchor (씬)        "나는 #102 다" + Floor · WalkableArea · SpawnPoint 들
```

| 조각 | 사는 곳 | 책임 |
|---|---|---|
| `AreaDefinition` | 에셋 | areaId · 표시명 · 보스 여부 · 탈출 목적지 |
| `AreaAnchor` | 층 루트 | 그 번호가 씬의 어느 오브젝트인지 |
| `SpawnPoint` | 층 자식 | 도착 좌표 **와 도착 후 바라볼 방향** |
| `AreaRegistry` | `Map` 루트 | 번호 → 층 해석, 활성 층 교체, 카메라 경계 |
| `AreaTransition` | Boot 상주 | 잠금 · 페이드 · 교체 · 이동 · 저장의 순서 |
| `Portal` | 층 자식 | "어디로" 만 말한다 |

### `AreaRegistry` 가 비활성까지 훑는 것이 핵심이다

각 층이 `OnEnable` 에서 스스로 등록하는 방식으로는 **절대 동작하지 않는다.**
포탈이 목적지를 물어볼 때 그 층은 아직 꺼져 있기 때문이다.
`GetComponentsInChildren<AreaAnchor>(includeInactive: true)` 를 `Awake` 에서 한 번 돌린다.

### 끄기가 켜기보다 먼저다

`WalkableArea` 가 `OnEnable/OnDisable` 로 `ServiceRegistry` 를 갱신한다.
켜기를 먼저 하면 새 구역이 등록된 직후 옛 구역의 `OnDisable` 이 돌아
"이미 등록되어 있어 덮어씁니다" 경고가 매 전환마다 찍힌다.
두 호출 사이에는 아무것도 실행되지 않으므로 순서만 지키면 빈틈은 없다.

## 5. 전환 순서

```
입력 잠금 → 페이드 아웃 → 구역 교체(+카메라 경계) → 도착 지점으로 Warp
          → 방향 세팅 → 카메라 스냅 → 세이브 → 페이드 인 → 잠금 해제
```

- **구역 교체는 페이드가 완전히 덮은 뒤에** 한다. 층 하나가 2만 칸짜리 타일맵이라 켜는 순간 프레임이 튄다
- 도착 지점은 `WalkableArea.TryFindWalkable` 을 한 번 거친다. 맵을 다시 그렸을 때 벽 속에 박히는 것을 막는다
- 카메라는 보간이 아니라 `SnapToTarget`. 보간에 맡기면 페이드 인 후에 화면이 흘러간다
- 세이브에 `areaId` 를 남긴다. 없으면 재시작 시 **옛 구역의 같은 좌표**에 선다

## 6. 상호작용은 포탈 전용이 아니다

`IInteractable` / `InteractableBehaviour` / `InteractionHub` 로 한 겹 뺐다.
히든 상자·아이템 줍기가 같은 흐름을 그대로 쓴다.

- 판정은 각 대상이 자기 트리거로 하고, **여럿이 겹쳤을 때 무엇을 고를지**만 허브가 정한다
- 입력을 `PlayerController` 가 아니라 허브가 읽는다. 그쪽은 입력과 이동만 담당해야 하고,
  상호작용이 없는 씬에서 그 코드를 들고 다니지 않게 한다 (005 §4 와 같은 이유)
- **화면 버튼과 키보드가 같은 경로를 탄다** (`InteractionHub.TryInteract`).
  `OnScreenButton` 으로 가상 게임패드 입력을 흉내내면 눌림 판정이 입력 시스템을 한 바퀴 돌아 동작이 갈릴 수 있다

### 두 가지 Unity 함정

1. **인터페이스 참조에는 Unity 의 널 비교가 걸리지 않는다.**
   `IInteractable` 로 들고 있으면 `== null` 이 C# 기본 참조 비교라 이미 `Destroy` 된 MonoBehaviour 도
   "살아 있음" 으로 나온다. `UnityEngine.Object` 로 캐스팅해야 오버로드된 비교가 적용된다.
2. **사용 버튼은 자기 자신을 `SetActive(false)` 로 끄면 안 된다.**
   `Update` 가 멈춰 다시 켤 주체가 사라진다. `CanvasGroup` 의 알파와 레이캐스트로만 숨는다.

## 7. 링크 오타는 정적으로 잡는다

번호와 문자열로만 이어져 있어 컴파일러가 잡아주지 못하고,
**잘못된 링크는 그 포탈을 실제로 밟기 전까지 드러나지 않는다.**
층이 9개라 전부 걸어서 확인하는 것은 현실적이지 않다.

`Pretty Knights > Areas > 0. 포탈 링크 점검 (변경 없음)` 이 씬을 훑는다.
프로젝트의 다른 에디터 도구와 마찬가지로 **변경 없는 점검 메뉴를 따로 둔다.**

## 8. 진행 범위

**Goblin 테마 3개 층만 먼저 붙인다.** 검증된 뒤 Orc(201~203) · Vampire(301~303) 로 복제한다.
아트 교체는 2026-08-08 이후 별도 작업.
