# 009 — 세로 모드의 화면과 진행

*2026-08-09 확정*

가로 모드가 한 바퀴 도는 것을 확인한 뒤, 세로 모드를 실제로 만들면서 정한 것들.
미결정 #8(세로/가로 기준 해상도 및 전환 동작)의 답이 여기 들어 있다.

---

## 1. 화면을 세 띠로 나눈다

기준 해상도 **1080 × 1920**. `Height Fraction` 은 처음 0.30 으로 잡았다가
**0.25 로 확정**했다 (2026-08-09) — 하단에 상점 6칸을 스크롤 없이 앉히려면
1440px 이 필요했다.

| 띠 | 높이 비율 | 내용 |
|---|---|---|
| 상단 HUD | 0.14 (269px) | 레벨 · 체력 · 재화 |
| **전투 화면** | **0.25 (480px)** | 카메라가 그리는 유일한 곳 |
| 하단 — 상점 | 0.61 (1171px) | 재화 · 상점 6칸 · 메뉴 |

숫자는 `StageViewport` 의 `Top Inset` · `Height Fraction` 두 칸이 정하고
하단은 **남은 자리**로 계산된다. 세 값을 각각 적으면 합이 1 을 넘는 조합을 만들 수 있다.

### 왜 UI 로 덮지 않는가

덮으면 카메라가 화면 전체(1920px)를 계속 그린다. 보이지도 않을 픽셀이 대부분이다.
뷰포트를 줄이면 그리는 픽셀이 **576px 로 줄어든다.** 모바일에서 이 차이는 발열이다.

### 뷰포트 밖은 지워지지 않는다

카메라는 자기 띠 안만 지운다. 나머지에는 직전 프레임이 남는다.
하단 판이 가려주지만 **상단 HUD 액자에는 구멍이 뚫려 있어** 그리로 비친다.
그래서 **화면 전체를 지우기만 하는 카메라를 한 대 더 둔다**
(Priority −10 · Culling Mask Nothing · Solid Color).

### `orthographicSize` 를 띠 비율만큼 줄인다

`Size` 는 화면 높이의 절반을 **월드 유닛**으로 정한다. 뷰포트만 줄이고 이 값을 두면
같은 세로 10유닛을 1/3 높이의 픽셀에 넣게 되어 **캐릭터가 3.3배 작아진다**
(찌그러지지는 않는다 — 가로도 함께 넓어지므로).

`size = 5 × 0.30 = 1.5` 로 줄이면 픽셀당 크기가 전체 화면과 같아지고,
**가로로 보이는 범위 5.625유닛까지 그대로**다. 세로 모드는 위아래만 잘린 셈이 된다.

## 2. 몬스터가 아니라 장애물을 부순다 (2026-08-09 수정)

처음에는 세로도 몬스터 사냥으로 잡았다가 **장애물 파밍**으로 바꿨다.

| | 가로 | 세로 |
|---|---|---|
| 대상 | 몬스터 | **부술 수 있는 장애물** |
| 나오는 방식 | 층 인구 상한 | 플레이어 주변에 계속 다시 뽑힌다 |
| 진행 | 토템 → 포탈 → 다음 층 | 없다. 끝없이 부순다 |
| 얻는 것 | 경험치 · 아이템 | 경험치 · 아이템 · **골드** |

가로의 층 구조(메인 토템 → 포탈 → 다음 층)를 세로에 옮기지 않는다.
사냥터는 **방 하나**면 된다. 구역 전환도 `AreaDefinition` 도 필요 없다.

### `FloorProps` 를 쓰지 않고 `ObstacleField` 를 새로 만든 이유

목적이 정반대다.

```
FloorProps (가로)     층의 지형을 만든다      → 다시 와도 그대로여야 한다
ObstacleField (세로)  파밍 대상을 만든다      → 부수는 족족 새로 나와야 한다
```

가로에서 배치가 고정인 것은 **오브젝트가 통행 경로를 만들기 때문**이고
(docs/design/map-objects.md), 세로에는 찾아갈 길이 없다.
한 컴포넌트에 두 성격을 넣으면 스위치 하나로 정반대로 동작하는 것이 된다.

구조는 `FloorPopulation`(몬스터) 쪽을 그대로 따랐다 — 플레이어 주변 고리에 뿌리고,
멀어지면 회수하고, 목표 수를 유지한다.

### 부서진 몸을 다시 쓴다

`Destructible.Bind` 가 HP·그림·**콜라이더**를 되돌린다.
콜라이더를 되살리지 않으면 두 번째로 뽑힌 장애물이 **통과되는 유령**이 된다.

## 3. 조작이 거의 없다 (2026-08-09 수정)

| | 누가 |
|---|---|
| 이동 · 대상 고르기 | `AutoBattle` |
| 기본 공격 | `AutoBattle` |
| 부수기 | 위와 같음 (장애물도 `IDamageable` 이다) |

**세로에는 스킬 버튼을 두지 않는다.** 하단은 대신 **상점**이 차지한다 (아래 4절).
스킬은 가로 모드의 것이다.

`AutoBattle` 은 대상을 `IDamageable` 로 찾으므로 장애물도 그대로 대상이 된다 —
고칠 것이 없었다.

### 모터의 주인은 `PlayerController` 하나다

`AutoBattle` 이 `CharacterMotor` 를 직접 몰지 않고 `PlayerController.Drive()` 로 넘긴다.
둘이 몰면 실행 순서에 따라 `PlayerController.Update` 가 그 값을 0 으로 덮어쓰는
프레임이 생겨 **가다 서다를 반복**한다. 증상만 봐서는 원인을 찾기 어려운 종류다.

`Drive` 로 넣은 값은 **한 프레임만 유효하다.** 모는 쪽이 멈추면 그 자리에 선다 —
남겨두면 자동이 꺼진 뒤에도 마지막 방향으로 계속 걷는다.

---

## 4. 하단은 상점이다 (2026-08-09 수정)

**골드를 쓰는 곳은 세로 모드에만 있다.** 가로는 벌기만 하고 쓰지 않는다.

```
세로   장애물을 부순다 → 골드 · 아이템 → 상점에서 쓴다      순환이 여기서 닫힌다
가로   몬스터를 잡는다 → 골드 · 아이템 → 쓸 곳은 세로에
```

두 모드를 오갈 이유가 이걸로 생긴다. 가로에서 번 것을 세로에서 쓰고,
세로에서 산 것으로 가로를 더 깊이 간다.

스킬은 가로 모드의 것이다 — `ISkillBar` 4칸은 그대로 두고 세로에는 두지 않는다.

---

## 5. 재화는 골드 하나로 시작한다

`Wallet` 을 따로 둔 이유는 종류가 늘어날 때 고칠 자리를 하나로 묶기 위해서다.
`PlayerRuntimeState` 에 `gold` 를 얹었다면 재화가 둘이 되는 순간
상태 · 세이브 · UI 세 곳을 함께 고쳐야 한다.

**가방과 가르는 기준은 "칸을 차지하는가" 다.** 골드는 칸도 상한도 없고
정렬 · 버리기 대상도 아니다. 아이템으로 만들면 30칸 격자에 절대 안 없어지는 칸이 하나 생긴다.

골드는 **표를 굴리지 않는 확정 지급**이다 (`MonsterDefinition.goldReward`).
잡을 때마다 0 이 나오면 파밍이 도는지 화면에서 읽히지 않는다.
경험치에 배수를 곱해 만들지 않은 것은 **레벨 커브와 경제를 따로 조절해야** 하기 때문이다.

---

## 6. 세로에서만 1.5배 당겨 본다

전투 화면이 480px 띠라 전체 화면과 같은 배율로는 캐릭터가 너무 작다.
**카메라를 1.5배 당기고 캐릭터도 1.5배로 키운다** (둘 다).

```
가로       size 5       가로 시야 5.625유닛   캐릭터 폭 0.72유닛 = 화면의 13%
세로       size 0.833   가로 시야 3.75유닛    캐릭터 폭 1.08유닛 = 화면의 29%
```

캐릭터를 키우는 쪽은 **세로 전용 프리팹**(`Player_Vertical`)이 맡는다.
공용 `Player.prefab` 을 건드리면 가로까지 커진다.

## 아직 정하지 않은 것

- **상점이 무엇을 파는가** — 스탯 강화(반복 구매)와 포션이 후보다.
  스탯 강화는 세이브에 강화 단계를 담아야 하므로 구조가 하나 더 붙는다
- 오프라인 보상 — 미결정 #5 와 같은 항목이다
- 세로에서 죽으면 어떻게 되는가. 지금은 부활 규칙이 없다
- 장애물 종류 — 지금은 18종 중 골라 쓰지만 세로 전용 아트가 있어야 자연스럽다
- 스킬 3종(전방 베기 · 관통 직선 · 광역 폭발)의 실제 수치
