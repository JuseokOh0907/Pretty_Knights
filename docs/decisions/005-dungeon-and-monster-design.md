## 0. 실제 제작 결과와의 차이 (2026-08-05)

Goblin 던전을 실제로 만든 결과 **§1 의 "방 = 화면 하나" 전제가 폐기됐다.**
아래 표가 현재 사실이다. §1 은 기록용으로 남긴다.

| | 이 문서의 원안 | **실제** |
|---|---|---|
| 공간 단위 | 방 하나 = 화면 하나 (16×8) | **연속된 대형 층.** 2F 만 170 × 264칸 |
| 방 이동 | 갭 + 페이드 전환 | 해당 없음 |
| 층 이동 | 파랑 포탈 | 층 레이어 (**포탈 없음**) |
| 보상 방 | 2층에 분기 | **없음** |
| 3층 | 보스 | **보스 (일치)** |
| 카메라 | 추적 불필요 | **추적 필수** |
| 몬스터 상한 | 방당 | **스포너 범위당** |

### 층마다 역할이 다르다 (2026-08-05)

크기 차이는 취향이 아니라 역할에서 나온다. **2층이 항상 가장 넓다.**

| 층 | 역할 | 크기 의도 |
|---|---|---|
| **1F** | 그 테마 몬스터의 **특성 안내**. 히든 아이템이 숨어 있다 | 보통 |
| **2F** | **사냥과 파밍**. 레벨업과 히든 상자를 노리는 층 | **아주 넓게** |
| **3F** | 보스와 1 대 1. 넓은 필드에서 크게 소환된 보스의 공격을 피하며 공략 | 보스 패턴에 맞춰 |

보스를 잡으면 **보상 포탈**이 열리고, 거기서 그 보스 전용 아이템을 준다.
전용 아이템을 전부 모으면 환생으로 이어지는 구상이지만 **지금은 구현하지 않는다.**

> 3F 크기는 보스 패턴에 종속된다. 패턴이 넓게 퍼지면 넓은 필드가 필요하고,
> 좁은 범위 패턴이면 작아도 된다. 실제로 Goblin 5,742 / Orc 6,369 대비
> Vampire 3F 는 1,722칸으로 작다.

### 테마마다 정체성이 다르다 (2026-08-05)

| 테마 | 성격 | 맵으로 표현한 방식 |
|---|---|---|
| **Goblin** | 기준점 | 넓고 트인 구조 |
| **Orc** | **물리 공격력이 강하다.** 보스를 뺀 개체는 스탯이 높은 만큼 **수가 적다** | **작게.** 회피 공간이 없어 정면 대결이 강제된다 |
| **Vampire** | 신체 능력보다 **마법 의존**. 범위 공격 회피가 핵심 | **작지만 벽이 많아** 이동이 어렵다 |

**벽 밀도가 이 의도를 그대로 보여준다.**

```
층            벽(Guide)     바닥      벽 : 바닥
Goblin 1F        1,370    12,147      1 : 8.9
Goblin 2F        5,179    20,035      1 : 3.9
Goblin 3F          312     5,742      1 : 18.4
Orc    1F          794     1,950      1 : 2.5     ← 조밀
Orc    2F        2,624     6,740      1 : 2.6     ← 조밀
Orc    3F          344     6,369      1 : 18.5
Vampire 1F         878     5,574      1 : 6.3
Vampire 3F       1,239     1,722      1 : 1.4     ← 미로
```

보스방끼리 비교하면 Goblin·Orc 는 벽 하나에 바닥 18칸인 트인 공간인데
Vampire 는 1.4칸이다. **13배 차이**다.

### Vampire 보스는 순간이동으로 미로를 우회한다

- **플레이어와 같은 크기.** 덩치로 누르지 않는다
- 이동 범위는 좁게, 대신 **순간이동 패턴**을 쓴다

이 선택이 경로 탐색 문제를 정면으로 해결한다.
벽 밀도 1:1.4 에서 A\* 가 필요했던 이유는 보스가 **걸어서** 쫓아와야 했기 때문인데,
순간이동은 벽을 무시하므로 그 요구가 사라진다.

**그리고 미로가 플레이어에게만 제약으로 남는다.**

```
플레이어   벽을 돌아가야 함     → 범위 공격 회피 경로가 제한된다
보스       벽을 무시하고 등장   → 압박이 끊기지 않는다
```

이 비대칭이 곧 "마법 의존 · 범위 공격 회피" 라는 테마 정체성이다.
Goblin·Orc 의 "크게 소환된 보스" 와 성격이 확실히 갈린다.

> **구현 시 필요한 것:** 순간이동 목적지가 벽 안이면 안 된다.
> `Physics2D.OverlapCircle` 로 Guide 콜라이더와 겹치는지 확인하고 실패 시 재시도한다.
> **스포너의 스폰 위치 검증과 같은 로직**이므로 한 번 만들어 양쪽에서 쓴다.
> `CharacterMotor.Warp()` 는 이미 있다.

> ⚠️ **일반 몬스터는 여전히 경로 탐색이 필요하다.**
> 순간이동은 보스 패턴이지 잡몹에게 주는 것이 아니다.
> 단순 조향은 트인 맵에서 문제가 안 드러나다가 벽이 많은 구간에서 망가진다.
> §6-1 의 그리드 A\* 는 그대로 유효하다.

## 1. (폐기) 공간 단위 — 방 = 화면 하나

> 아래는 원안이며 실제와 다르다. §0 을 따를 것.

- 방 하나가 가로 모드 화면 하나에 들어간다 (기준 `18 × 10` 칸, 내부 `16 × 8`).
  타일 1칸 = 1 월드 유닛이므로 ortho size 약 4.5 에서 정확히 맞는다.
- **카메라 추적이 필요 없다.** 방 중앙 고정.

### 방 형태

9슬라이스 8조각으로 **축 정렬 다각형은 무엇이든** 만들 수 있다.
사각형뿐 아니라 L자 · 십자 · 아령 · 벽감 · 계단식이 전부 가능하며 **타일 소모는 동일하다.**

조각 선택 규칙은 볼록/오목이 아니라 **"그 칸의 어느 변에 벽이 필요한가"** 다.
위+오른쪽이 필요하면 `03_top_right`, 안쪽으로 꺾이는 자리도 같은 규칙을 따른다.

| 방 | 권장 형태 |
|---|---|
| 진입 · 계단 | 사각형 (방향 파악이 즉시 돼야 함) |
| 전투 | L자 · 벽감 · 계단식 (시야가 꺾여 몬스터 배치에 의미가 생김) |
| 열쇠 | 십자 (분기로 탐색 동기 부여) |
| 보상 | 벽감 (작고 목적이 분명한 공간) |
| 보스 | 넓은 사각형 + 오브젝트 기둥 |

> **도넛(중앙 기둥)은 타일로 만들지 않는다.**
> 9슬라이스는 "벽이 바닥을 감싸는" 방향으로 그려져 있어 기둥에 쓰면 바깥면 자리에
> 안쪽면 그림이 들어간다. 기둥은 `Objects/` 의 128px 자산(정확히 2×2칸)으로 대체한다.

## 2. 방 이동 — 갭 + 페이드 전환

문 타일은 사용하지 않는다. **벽(Guide)을 비운 구간**이 출입구다.

- 갭 폭 **2칸**. 1칸도 물리적으로는 지나가지만 대각선 입력에서 걸린다.
- 갭은 **직선 벽 구간에만** 낸다. 모서리 조각은 두 방향 벽을 동시에 들고 있어
  한쪽만 비울 수 없다. 갭 양옆에 직선 조각이 1칸씩 필요하므로
  **출입구를 낼 변은 최소 5칸**이어야 한다.
- 플레이어가 갭 밖으로 계속 밀면 **페이드 아웃 → 방 전환 → 짝 갭 앞 배치 → 페이드 인**.
- 나가는 방향과 들어오는 위치는 짝이다. 오른쪽으로 나가면 다음 방 **왼쪽 갭 앞**에 선다.
- 페이드(0.2~0.3초)가 로딩을 가리므로 방을 씬으로 쪼갤 필요가 없다.

**복도는 던전 내부에 쓰지 않는다.** 갭 전환의 템포를 끊는다.
복도 구조는 던전 입구까지 가는 **숲길**에 쓴다 (길을 강제하는 나무·바위 오브젝트 추가 제작 예정).

## 4. 몬스터

### 프리팹과 데이터

플레이어와 **동일한 프리팹 구조**를 쓰고 `MonsterDefinition`(SO)과 Animator 를 갈아 끼워
움직임을 제어한다. 스폰 지점은 방 단위로 지정하고 그 지점에서 프리팹을 소환한다.

### 스폰 · 리스폰 (2026-08-05 갱신)

맵이 연속된 대형 층이 되면서 **방당 상한이 성립하지 않는다. 스포너 범위당 상한**으로 간다.

- 스포너마다 **범위**와 그 안의 **동시 존재 상한**을 둔다.
- 상한보다 적어지는 순간 — 즉 **한 마리라도 처치된 시점** — 부터 리스폰 쿨타임이 돈다.
- **스포너는 플레이어가 가까워지면 켜진다.**

#### 켜고 끄는 책임을 나눈다

| | 누가 | 왜 |
|---|---|---|
| **꺼진 스포너를 켠다** | `SpawnerDirector` 가 간격 검사 | 대다수인 꺼진 스포너가 각자 `Update` 를 돌지 않게 |
| **켜진 스포너를 끈다** | 스포너 자신이 간격 검사 | 켜져 있는 것은 보통 몇 개뿐 |

**진짜 비용은 거리 계산이 아니라 `Update()` 개수다.**
`Vector2.Distance` 는 수 나노초라 스포너 300개를 초당 5회 순회해도
초당 1,500회에 불과하다. 반면 MonoBehaviour 하나당 `Update` 호출에는
네이티브↔매니지드 전환 오버헤드가 붙는다.

- 검사 반경은 **등록된 스포너의 최대 반경 × 1.5** 로 디렉터가 자동 산출한다
- 비활성 거리는 활성 거리 × 1.3 (이력). 같은 값이면 경계에서 켜졌다 꺼졌다 반복한다
- **공간 분할(균일 격자)은 지금 넣지 않는다.** 전체 순회가 공짜인 규모라
  얻는 것 없이 복잡도만 오른다. 스포너가 수천 개가 되면 그때 도입한다
- 스캔은 `PlayerController` 가 아니라 디렉터가 한다.
  플레이어는 입력과 이동만 담당해야 하고, 스포너가 없는 씬에서도
  그 코드를 들고 다니지 않게 한다

#### 아직 안 쓰는 것

보주와 포탈은 **Goblin 맵에 없다.** 층 레이어로 이동하므로 필요가 없어졌다.
다른 던전에서 다시 필요해지면 그때 되살린다.

> **보주 파괴 시 리스폰도 함께 멈춘다.**
> 안 그러면 포탈로 걸어가는 동안 계속 새 몬스터에게 쫓긴다.

### 배회와 추격

- 오브젝트 배치가 **이동 가능 범위를 결정한다.** 오브젝트는 2×2칸이며 콜라이더를 갖는다.
- 일정 거리 안에 플레이어가 들어오면 추격으로 전환한다
  (`MonsterDefinition.DetectRange` 가 이미 있다).

## 5. 환생(Rebirth)

- 던전 탈출 스킬을 쓰거나 던전 밖으로 나오면 **클리어 기록이 남는다.**
- **모든 던전의 보스를 처치**하면 검을 이용한 환생이 열린다.
- 환생할수록 몬스터와 플레이어가 함께 강해진다.
- 현재는 환생 후에도 맵이 동일하다. **추후 환생마다 층이 추가로 생성된다.**

## 6. 검토 필요

### 6-1. NavMesh 는 2D 에서 그대로 쓸 수 없다 ⚠️

Unity NavMesh 는 **XZ 평면(3D) 기준**이다. 이 프로젝트는 XY 평면 2D 탑다운이라
`NavMeshAgent` 가 의도대로 동작하지 않는다.

- `com.unity.modules.ai` 는 설치되어 있으나 이는 런타임 모듈일 뿐이다
- 런타임 베이크용 `com.unity.ai.navigation` 은 **미설치**이며, 깔아도 2D 대응은 되지 않는다
- 2D 로 쓰려면 `NavMeshPlus` 같은 서드파티 포크가 필요하다

**대안 권장: 방 단위 그리드 A\***

방 하나가 `16 × 8 = 128칸`이다. 이 규모에서 A\* 는 한 번 계산에 수십 마이크로초 수준이고
**패키지 의존성이 0**이다. 타일맵과 오브젝트 콜라이더에서 통행 가능 격자를 만들면
NavMesh 베이크·굽기 과정 자체가 사라진다.

방이 닫혀 있고 화면 하나 크기라는 이 게임의 구조가 오히려 A\* 에 유리하다.

### 6-2. 몬스터 애니메이션 방식 — 결정 003 과 충돌

결정 003 은 **하이브리드**(플레이어 Animator / 몬스터 경량 스프라이트)를 택했다.
근거는 "자동 사냥에서 동시 수십 마리"였다.

이번 구상은 몬스터도 플레이어와 같은 프리팹·Animator 를 쓴다.
**방당 동시 상한이 10 마리 이하라면 Animator 로 통일해도 무방하고 구현이 훨씬 단순하다.**
상한이 정해지면 003 을 갱신한다.

### 6-3. 층 수를 상수로 두지 않는다

"환생마다 층 추가"가 예정되어 있으므로 층 수를 코드 상수로 박으면 안 된다.
`DungeonDefinition` 이 층 목록을 데이터로 들고, 세이브는 **환생 횟수 + 던전별 클리어 기록**을
저장하는 형태로 처음부터 만든다.

### 6-4. 오브젝트 배치 밀도

오브젝트가 2×2칸을 차지하므로 `16 × 8` 방에서 4개만 놓아도 통행 가능 면적의 12.5%가 사라진다.
추격 경로가 막히지 않도록 **방당 오브젝트 상한**을 정해야 한다.

## 7. 만들어야 할 데이터 계층

```
RoomDefinition    (SO)  방 형태, 갭 방향 4개, 스폰 지점, 오브젝트 배치, 보주 유무
FloorDefinition   (SO)  방 배치와 연결 그래프
DungeonDefinition (SO)  층 목록, 테마, 보스
RoomTransition          갭 트리거 → 페이드 → 방 전환 → 짝 갭 배치
MonsterSpawner          상한·쿨타임·보주 연동
```

전부 씬 비종속 데이터이므로 결정 003 의 Boot + Additive 구조에 그대로 얹힌다.

## 8. 미해결

- 방당 몬스터 동시 상한 (6-2 의 결론이 여기에 걸림)
- 리스폰 쿨타임 수치
- 환생 시 플레이어·몬스터 성장 배율
- 숲길 타일셋의 구성 (길 · 나무 · 바위)
