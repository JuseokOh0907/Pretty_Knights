# 005. 던전 구조와 몬스터 설계

- **상태:** 구상 확정 (일부 항목은 아래 "검토 필요" 참조)
- **결정일:** 2026-08-02

이 문서는 미결정 #7(맵 토폴로지 및 첫 지역 테마)의 대부분을 대체한다.

---

## 1. 공간 단위 — 방 = 화면 하나

- 방 하나가 가로 모드 화면 하나에 들어간다 (기준 `18 × 10` 칸, 내부 `16 × 8`).
  타일 1칸 = 1 월드 유닛이므로 ortho size 약 4.5 에서 정확히 맞는다.
- **카메라 추적이 필요 없다.** 방 중앙 고정.
  스크롤 카메라가 없다는 것은 모바일에서 컬링·드로우콜 부담이 통째로 빠진다는 뜻이다.

### 방 형태

9슬라이스 8조각으로 **축 정렬 다각형은 무엇이든** 만들 수 있다.
사각형뿐 아니라 L자 · 십자 · 아령 · 벽감 · 계단식이 전부 가능하며 **타일 소모는 동일하다.**

조각 선택 규칙은 볼록/오목이 아니라 **"그 칸의 어느 변에 벽이 필요한가"** 다.
위+오른쪽이 필요하면 `03_top_right`, 안쪽으로 꺾이는 자리도 같은 규칙을 따른다.

| 방 | 권장 형태 |
|---|---|
| 진입 · 계단 | 사각형 (방향 파악이 즉시 돼야 함) |
| 전투 | L자 · 벽감 · 계단식 (시야가 꺾여 몬스터 배치에 의미가 생김) |
| 열쇠 | 십자 (분기로 탐색 동기 부여) |
| 보상 | 벽감 (작고 목적이 분명한 공간) |
| 보스 | 넓은 사각형 + 오브젝트 기둥 |

> **도넛(중앙 기둥)은 타일로 만들지 않는다.**
> 9슬라이스는 "벽이 바닥을 감싸는" 방향으로 그려져 있어 기둥에 쓰면 바깥면 자리에
> 안쪽면 그림이 들어간다. 기둥은 `Objects/` 의 128px 자산(정확히 2×2칸)으로 대체한다.

## 2. 방 이동 — 갭 + 페이드 전환

문 타일은 사용하지 않는다. **벽(Guide)을 비운 구간**이 출입구다.

- 갭 폭 **2칸**. 1칸도 물리적으로는 지나가지만 대각선 입력에서 걸린다.
- 갭은 **직선 벽 구간에만** 낸다. 모서리 조각은 두 방향 벽을 동시에 들고 있어
  한쪽만 비울 수 없다. 갭 양옆에 직선 조각이 1칸씩 필요하므로
  **출입구를 낼 변은 최소 5칸**이어야 한다.
- 플레이어가 갭 밖으로 계속 밀면 **페이드 아웃 → 방 전환 → 짝 갭 앞 배치 → 페이드 인**.
- 나가는 방향과 들어오는 위치는 짝이다. 오른쪽으로 나가면 다음 방 **왼쪽 갭 앞**에 선다.
- 페이드(0.2~0.3초)가 로딩을 가리므로 방을 씬으로 쪼갤 필요가 없다.

**복도는 던전 내부에 쓰지 않는다.** 갭 전환의 템포를 끊는다.
복도 구조는 던전 입구까지 가는 **숲길**에 쓴다 (길을 강제하는 나무·바위 오브젝트 추가 제작 예정).

## 3. 층 구성

층 3개 고정, 층당 방 수로 테마 난이도를 차등한다.

| 테마 | 총 방 | 층당 |
|---|---|---|
| Goblin | 9 | 3 |
| Orc | 12 | 4 |
| Vampire | 15 | 5 |

보상 방은 **2층에만** 둔다. 1층은 진입 부담이 없어야 하고 3층은 보스와 분기가 겹친다.

포탈 3종의 역할은 아트 파일명이 이미 지정하고 있다.

| 자산 | 역할 |
|---|---|
| `portal_blue_entrance` | 진입 / 다음 층 |
| `portal_gold_reward` | 보상 방 (`01_reward_room_key` 필요) |
| `portal_crimson_boss` | 보스 |

## 4. 몬스터

### 프리팹과 데이터

플레이어와 **동일한 프리팹 구조**를 쓰고 `MonsterDefinition`(SO)과 Animator 를 갈아 끼워
움직임을 제어한다. 스폰 지점은 방 단위로 지정하고 그 지점에서 프리팹을 소환한다.

### 스폰 · 리스폰

- 방(또는 층)마다 **동시 존재 상한**을 둔다.
- 상한보다 적어지는 순간 — 즉 **한 마리라도 처치된 시점** — 부터 리스폰 쿨타임이 돈다.
- 방에는 몬스터를 생성하는 **보주**가 있다.
  보주를 부수면 **포탈이 생성**되어 다음 방으로 이동할 수 있다.

> **보주 파괴 시 리스폰도 함께 멈춘다.**
> 안 그러면 포탈로 걸어가는 동안 계속 새 몬스터에게 쫓긴다.

### 배회와 추격

- 오브젝트 배치가 **이동 가능 범위를 결정한다.** 오브젝트는 2×2칸이며 콜라이더를 갖는다.
- 일정 거리 안에 플레이어가 들어오면 추격으로 전환한다
  (`MonsterDefinition.DetectRange` 가 이미 있다).

## 5. 환생(Rebirth)

- 던전 탈출 스킬을 쓰거나 던전 밖으로 나오면 **클리어 기록이 남는다.**
- **모든 던전의 보스를 처치**하면 검을 이용한 환생이 열린다.
- 환생할수록 몬스터와 플레이어가 함께 강해진다.
- 현재는 환생 후에도 맵이 동일하다. **추후 환생마다 층이 추가로 생성된다.**

## 6. 검토 필요

### 6-1. NavMesh 는 2D 에서 그대로 쓸 수 없다 ⚠️

Unity NavMesh 는 **XZ 평면(3D) 기준**이다. 이 프로젝트는 XY 평면 2D 탑다운이라
`NavMeshAgent` 가 의도대로 동작하지 않는다.

- `com.unity.modules.ai` 는 설치되어 있으나 이는 런타임 모듈일 뿐이다
- 런타임 베이크용 `com.unity.ai.navigation` 은 **미설치**이며, 깔아도 2D 대응은 되지 않는다
- 2D 로 쓰려면 `NavMeshPlus` 같은 서드파티 포크가 필요하다

**대안 권장: 방 단위 그리드 A\***

방 하나가 `16 × 8 = 128칸`이다. 이 규모에서 A\* 는 한 번 계산에 수십 마이크로초 수준이고
**패키지 의존성이 0**이다. 타일맵과 오브젝트 콜라이더에서 통행 가능 격자를 만들면
NavMesh 베이크·굽기 과정 자체가 사라진다.

방이 닫혀 있고 화면 하나 크기라는 이 게임의 구조가 오히려 A\* 에 유리하다.

### 6-2. 몬스터 애니메이션 방식 — 결정 003 과 충돌

결정 003 은 **하이브리드**(플레이어 Animator / 몬스터 경량 스프라이트)를 택했다.
근거는 "자동 사냥에서 동시 수십 마리"였다.

이번 구상은 몬스터도 플레이어와 같은 프리팹·Animator 를 쓴다.
**방당 동시 상한이 10 마리 이하라면 Animator 로 통일해도 무방하고 구현이 훨씬 단순하다.**
상한이 정해지면 003 을 갱신한다.

### 6-3. 층 수를 상수로 두지 않는다

"환생마다 층 추가"가 예정되어 있으므로 층 수를 코드 상수로 박으면 안 된다.
`DungeonDefinition` 이 층 목록을 데이터로 들고, 세이브는 **환생 횟수 + 던전별 클리어 기록**을
저장하는 형태로 처음부터 만든다.

### 6-4. 오브젝트 배치 밀도

오브젝트가 2×2칸을 차지하므로 `16 × 8` 방에서 4개만 놓아도 통행 가능 면적의 12.5%가 사라진다.
추격 경로가 막히지 않도록 **방당 오브젝트 상한**을 정해야 한다.

## 7. 만들어야 할 데이터 계층

```
RoomDefinition    (SO)  방 형태, 갭 방향 4개, 스폰 지점, 오브젝트 배치, 보주 유무
FloorDefinition   (SO)  방 배치와 연결 그래프
DungeonDefinition (SO)  층 목록, 테마, 보스
RoomTransition          갭 트리거 → 페이드 → 방 전환 → 짝 갭 배치
MonsterSpawner          상한·쿨타임·보주 연동
```

전부 씬 비종속 데이터이므로 결정 003 의 Boot + Additive 구조에 그대로 얹힌다.

## 8. 미해결

- 방당 몬스터 동시 상한 (6-2 의 결론이 여기에 걸림)
- 리스폰 쿨타임 수치
- 환생 시 플레이어·몬스터 성장 배율
- 숲길 타일셋의 구성 (길 · 나무 · 바위)
